## 1. 오늘 배포가 하루 종일 안 나간 이유 (원인 3개, 모두 코드로 고쳤음)

운영은 07-26 05:25Z 이후 `1a272c9`(N10) 에서 멈춰 있었다. 그 뒤 푸시가 여러 번 있었지만
하나도 배포되지 않았다. 원인은 서로 다른 세 가지였다.

**(가) 링크 점검이 영원히 기다렸다.** `scripts/check-links.mjs` 는 약 200개 경로를 순차로
크롤하는데 요청당 상한이 없었다. DB 가 느려진 사이 동적 라우트 하나가 응답을 붙잡자
배포 실행 하나가 **3시간** 매달렸다. 요청당 20초 상한을 넣었고, 타임아웃을
"끊긴 링크 아님"으로 넘기지 않고 **응답없음**이라는 별도 사실로 남겨 배포를 막게 했다.
(못 받은 응답은 200 도 404 도 아니다.)

**(나) 멈춘 실행이 최신 코드를 덮을 수 있었다.** 동시 실행 그룹이 없어 "나중에 끝난 쪽이
이긴다"가 되고, 배포 순서가 커밋 순서와 무관해진다. `concurrency: cancel-in-progress` 와
잡 35분·링크 점검 12분 상한을 넣었다.

**(다) 주석 한 줄이 시크릿 스캐너에 걸렸다.** `lib/seo/google-oauth.ts` 주석에 환경변수
예시를 적으면서 PEM 개인키 머리글을 문자 그대로 넣었다. 실제 키는 한 글자도 없지만
gitleaks 의 private-key 규칙은 **머리글만 보고** 잡는다. 배포는 checkout 직후 51초 만에
죽었고, 원인은 CI 로그를 열기 전에는 보이지 않았다.
예시를 말로만 설명하도록 바꾸고, 같은 검사를 로컬에서 돌릴 수 있게
`npm run check:secret-markers` 를 만들어 deploy.yml 에도 한 단계로 넣었다.

**(라) 그리고 (가)를 고치면서 제가 반대쪽으로 문을 잠갔습니다.** 요청 상한을 넣을 때
타임아웃을 "끊긴 링크"와 똑같이 취급해 배포를 막게 했습니다. 그런데 DB 가 계속 느린
상태라 200개 경로 중 하나만 20초를 넘겨도 배포가 막혔고, **그 느림을 고치는 커밋들이
바로 그 이유로 배포되지 못했습니다.** 오후 내내 배포가 안 나간 건 이것 때문일 가능성이
가장 큽니다.

사실을 세 갈래로 나눠 다시 짰습니다. 끊긴 링크(4xx/5xx)는 **사이트에 대한 사실**이니
지금도 배포를 막습니다. 응답 없음(타임아웃)은 **그 순간에 대한 사실**이라 30초로 한 번 더
잡아 보고, 그래도 안 되면 로그에 "응답없음"으로 크게 남기되 소수면 배포는 통과시킵니다.
다만 그 수가 5개를 넘으면 그건 다시 사이트에 대한 사실이라 막습니다.
타임아웃을 200 처럼 조용히 넘기는 일은 없습니다 — 못 받은 응답은 200 도 404 도 아닙니다.

## 2. 결정 필요: Supabase 프로젝트 컴퓨트 크기 (유료 — 내가 못 함)

**조직 플랜을 Pro 로 올린 것과 프로젝트 인스턴스 크기는 별개 설정이다.**
Pro 로 올려도 인스턴스는 그대로다. 지금 인스턴스가 오늘 장애의 뿌리다.

측정한 사실(추정 아님):

| 항목 | 값 |
|---|---|
| `shared_buffers` | 229 MB |
| `effective_cache_size` | 384 MB |
| `max_connections` | 60 |
| `market_transactions` 크기 | 700 MB (heap 558 MB) |
| 행 수 | 592,610 (dead 48,944) |

**표 하나가 인스턴스 RAM 전체보다 크다.** 그래서 작업 집합이 캐시에 못 들어간다.

CPU 고갈의 결정적 증거 — 같은 질의를 연달아 두 번 돌렸다:

```
1회차  Aggregate (actual time=3687.419..3687.420)
       Buffers: shared hit=43        ← 디스크 읽기 0, 전부 캐시
       Execution Time: 3687.798 ms
2회차  (동일 질의)  Execution Time: 77.064 ms
대조군  explain analyze select 1  →  Execution Time: 0.093 ms
```

디스크를 한 번도 읽지 않은 43 buffer 짜리 질의가 한 번은 3.7초, 다음 번은 77ms 다.
I/O 문제도 인덱스 문제도 아니다 — **백엔드가 CPU 에서 밀려나고 있다.**
이 상태가 CI 의 순차 링크 크롤을 그대로 멈춰 세웠다.

→ **Project Settings → Compute and Disk** 에서 인스턴스를 올릴지는 **비용이 드는 사업 판단**이다.
사실만 적어 두고 나는 아무것도 사지 않는다. 올리지 않기로 해도 서비스는 돌아가지만,
백필·ANALYZE 가 겹치는 시간대에 오늘 같은 정체가 재발할 수 있다.

### 내가 지금 할 수 있는 만큼은 했다

`market_transactions.raw`(jsonb, 평균 570바이트)가 ANALYZE 비용을 지배하고 있었다.
autovacuum ANALYZE 가 표본 30,000행을 다 읽고도 `computing statistics` 단계에서
**8,600초(2시간 24분)** 동안 CPU 만 태우며 다른 백엔드를 밀어냈다.
나머지 컬럼은 전부 50바이트 이하다.

`raw` 를 조건으로 거르는 실행 경로가 없다 — 유일한 참조는 20260725042611 의 1회성
백필(`raw->>'cdealType'`)이고 그 결과는 이미 `is_cancelled` 컬럼과 인덱스로 물질화돼 있다.
그래서 `ALTER COLUMN raw SET STATISTICS 0` 을 적용했다. 파괴적 변경이 아니고
플래너 회귀 위험도 없다. 되돌리려면 `SET STATISTICS -1` 한 줄이다.

## 3. 아직 보고하지 않았던 데이터 결함 — 도시 간 중복 행

`market_transactions` 에 **같은 거래가 여러 도시에 복제된** 행이 있다.
행 내용의 md5 지문으로 묶어 확인했다:

| 지문 | region_name 들 | 행 수 |
|---|---|---|
| `32d16ce1…` | 광주·대구·대전·부산·울산·인천 동구 | 320 |
| `b5ee9662…` | 대구·대전·부산·울산·인천 중구 | 505 |
| `1638c73d…` | 광주·대구·부산·울산 북구 | 1,569 |
| `8cda5925…` | 광주·대구·부산·울산 남구 | 1,421 |
| `2c8c42d5…` | 광주·대구·대전·부산 서구 | 482 |

서울 중구만 정상이다. **지금 쓰는 ETL 은 `region_code` 를 올바로 넣는다** — 이 행들은
제거된 옛 ETL 이 남긴 레거시다. 즉 새로 생기지는 않는다.

영향: 위 구(區) 이름을 쓰는 광역시들의 거래 건수·평균가가 서로 섞여 부풀려 보인다.

정리는 **행 삭제**라서 내가 임의로 하지 않는다(파괴적 변경). 원하시면
"어느 region_code 를 정답으로 볼지" 기준을 정해 주시면 그 기준대로 지우는
마이그레이션을 써서 올리겠다. 그 전까지는 이 문서가 유일한 기록이다.
