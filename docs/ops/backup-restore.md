# SOP — DB 백업·복구 (v1, 2026-08-17)

> 백업은 "있다"가 아니라 "복구해 봤다"가 기준이다. 현재 상태: Supabase 관리형
> 백업에 의존 중이며 **설정 확인과 복구 리허설이 미실시** — 이 문서가 그 절차다.
> (대시보드 확인은 MFA 잠금 해제 후 가능 — owner-todo 참조)

## 1. 현재 확인해야 할 것 (MFA 해제 후 1회)

- [ ] Supabase → Database → Backups: 일일 백업 활성 여부·보존 기간
- [ ] PITR(Point-in-Time Recovery) 활성 여부 — 유료 옵션이면 비용 대비 판단
      (사용자 데이터가 늘기 시작하면 활성 권장)
- [ ] 백업 알림: 실패 시 통지가 어디로 오는지

## 2. 코드·설정의 백업 (이미 확보)

- 코드: GitHub 원격이 원천 (로컬·샌드박스는 사본)
- 스키마: supabase/migrations 원장 — **바이트 단위 원장 규율 게이트로 검증됨**
  (check-migration-ledger). 스키마는 언제든 재구축 가능
- env: Vercel 프로젝트 + GH Secrets 이중 보관 (2026-08-17부터)

## 3. 분기 복구 리허설 (분기 1회, 30분)

1. 새 임시 Supabase 프로젝트(또는 브랜치)에 최신 백업 복원
2. 핵심 테이블 행수 대조: inspection_notes · auth.users · point 원장 ·
   social_uploads · region_demand_requests
3. 마이그레이션 원장 최신 버전과 복원본 스키마 일치 확인
4. 결과를 이 문서 하단 "리허설 기록"에 한 줄 추가 (일시·소요·이슈)
5. 임시 프로젝트 삭제

## 4. 실제 복구 판단 기준

- 오염 범위가 특정 테이블·시간대: PITR(가능 시) 또는 백업에서 해당 테이블만 선별 복원
- 전면 장애: 최신 백업 전체 복원 → 복원 후 결제·포인트 원장은 토스 대사로 검증
- **복구보다 먼저 기록**: 무엇이 언제부터 잘못됐는지 타임라인부터
