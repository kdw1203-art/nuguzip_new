# standalone(홈 화면에 추가) 모드 안전영역 점검 — 2026-08-05

소유자가 아이폰 사파리 캡처를 주면서 "상단 주소창과 하단 뒤로가기가 화면을 너무
많이 먹는다"고 했다. 그 답은 홈 화면에 추가해서 standalone 으로 여는 것인데,
**standalone 은 화면을 더 주는 대신 안전영역을 앱에 떠넘긴다.** 브라우저 탭
모드에서는 하단 툴바가 홈 인디케이터를 덮어 주기 때문에 `env(safe-area-inset-bottom)`
이 0 이고, 그래서 **탭 모드에서 아무 문제가 없어도 standalone 에서만 깨지는
종류의 버그가 따로 있다.** 이 점검은 그 차이만 본다.

## 어떻게 쟀나 — 추측 대신 실측이 가능해졌다

지금까지 이런 건 "아마 괜찮을 것"으로 넘겼다. 실기기가 없으면 못 잰다고 생각했기
때문이다. 이번에 CDP 로 안전영역을 강제로 넣을 수 있다는 걸 확인했다:

```js
const cdp = await ctx.newCDPSession(page);
await cdp.send("Emulation.setSafeAreaInsetsOverride", {
  insets: { top: 0, bottom: 34, left: 0, right: 0 },
});
```

Chromium 141 에서 동작한다. 넣은 값이 실제로 `env(safe-area-inset-*)` 로 들어오는지
프로브 엘리먼트의 계산된 패딩을 되읽어 확인했다(넣은 34 → 읽은 34px). 이제
standalone 레이아웃은 **논증 대상이 아니라 측정 대상이다.**

두 모드를 이렇게 잡았다.

- **브라우저(탭)**: 390×734, 인셋 전부 0. 아이폰에서 사파리 하단 툴바가 홈
  인디케이터를 덮으므로 bottom 인셋이 0으로 온다.
- **standalone**: 390×844, `bottom: 34`, `top: 0`. top 이 0인 건
  `apple-mobile-web-app-status-bar-style` 이 `default` 라 콘텐츠가 상태바 **아래**에서
  시작하기 때문이다(`black-translucent` 였다면 top 인셋을 받아야 한다).

`scripts/audit-standalone-safearea.mjs` 로 `/`, `/map`, `/listings`, `/notes`,
`/town` 다섯 경로에서 최상위 `position: fixed` 요소의 화면 좌표를 두 모드로 재고,
화면 밖으로 나가는 것 · 탭 가능한 것끼리 겹치는 쌍 · **홈 인디케이터 자리로
내려온 컨트롤**을 골라냈다(중첩 fixed 와 `pointer-events: none` 은 뺐다 — 안
그러면 없는 버그가 잔뜩 나온다).

## 실측 결과

**탭바는 홈 인디케이터를 정확히 비껴간다.**

| | 탭바 위치 | 뷰포트 | 아래 여백 |
|---|---|---|---|
| 브라우저(탭) | 670→728 | 734 | 6px |
| standalone | 752→810 | 844 | **34px** |

`TabBar.tsx` 의 `bottom: max(6px, env(safe-area-inset-bottom, 0px))` 이 의도대로
동작한 결과다. 탭 모드에서는 인셋이 0이라 6px 이 이기고, standalone 에서는 34가
이겨 홈 인디케이터 위로 올라선다. **6px 을 그냥 `bottom: 6px` 로 적었다면 탭
모드에서는 똑같이 보이면서 standalone 에서만 인디케이터에 깔렸을 것이다.**

**/town 의 「글쓰기」 FAB 도 탭바와 부딪히지 않는다.** 606→658(탭, 탭바까지 12px)
→ 682→734(standalone, 18px). standalone 에서 오히려 더 벌어진다.

**`/` 의 클로즈 베타 안내는 겹침으로 잡히지만 그 자체는 버그가 아니다.**
`div.fixed.inset-0` 가 화면 전체를 덮는 모달이라 탭바와 겹친 것으로 보고된다 —
모달이 아래를 막는 건 의도다. 다만 이 모달이 있어서 `/` 에서는 자동화 클릭이
전부 막힌다는 걸 기록해 둔다(다음 점검은 `/listings` 에서 시작하는 게 빠르다).
**그리고 이 모달 "안"에서 진짜 결함이 나왔다 — 아래 두 번째 절.**

## 결함 1 — 바닥에 붙는 시트의 버튼이 홈 인디케이터 자리에 있었다

바깥 사각형만 보면 아무것도 안 나온다. 스크림은 원래 바닥까지 덮는 게 맞으니까.
안에 든 컨트롤을 재 보니 이렇게 나왔다(390×844, inset-bottom 34).

```
카드(시트) 442→844
  «의견 보내기» 783→824  아래여백 20   ← 34px 인디케이터 자리 안으로 14px
  «확인했어요»  783→824  아래여백 20   ← 같음
```

원인은 공용 `app/components/ui/Modal.tsx` 의 패널이 모바일에서 `items-end`,
즉 **화면 바닥에 붙는 시트**인데 아래 여백이 `p-5` 의 20px 고정이었다는 것이다.
탭 모드에서는 인셋이 0이라 20px 이 그대로 20px 여서 멀쩡해 보인다. 같은 모양이
저장소에 셋 있었다.

| 자리 | 고치기 전 아래 여백 | 사용처 |
|---|---|---|
| `ui/Modal.tsx` 패널 | 20px 고정 | 공용 모달 6곳(베타 안내 포함) |
| `UpgradePaywall.tsx` 스크림 | 16px 고정 | 402·쿼터 페이월 |
| `map/ComplexInfoPanel.tsx` 하단 CTA 바 | 12px 고정 | 지도 단지 시트 — 「전체 화면으로 더 자세히 보기」 |

셋 다 아래 여백에 인셋을 더하고, 가운데로 뜨는 `sm` 이상에서는 원래대로
되돌렸다(안 붙는 쪽에 인셋을 더하면 빈 띠만 생긴다). 방식은 이미 저장소에 있던
`SoftSignupProvider` 의 `pb-[max(env(safe-area-inset-bottom,0px),16px)] sm:pb-0`
을 따랐다 — **한 곳은 이미 알고 있었고 세 곳이 몰랐다.**

고친 뒤 같은 방식으로 다시 쟀다: `783→824`(아래여백 20) → **`749→790`(아래여백
54 = 인셋 34 + 여백 20)**. 새 유틸리티가 실제로 산출됐는지도 빌드 CSS 에서
확인했다(`padding-bottom:calc(20px + env(safe-area-inset-bottom,0px))` 외 2종) —
지난 웨이브에서 선언 없는 클래스가 전 검사를 통과한 적이 있어서 이 단계를 뺀다.

**검사기가 이 결함을 실제로 잡는지도 확인했다.** 고쳐 놓고 "0건"이 나오는 건
아무것도 증명하지 않는다 — 검사기가 그냥 아무것도 안 보고 있어도 0건이다.
그래서 수정 전 패딩(20px 고정)을 스타일로 되돌려 주입하고 다시 돌렸더니
**2건을 정확히 집어냈다.** 그 상태를 제거하니 0건. 0건이 뜻을 갖는 건 이 확인을
거친 다음이다.

덧붙여 침범 판정을 **컨트롤 기준으로만** 하도록 바꿨다. 처음엔 고정 요소의
바깥 사각형으로 쟀는데, 그러면 전체 화면 스크림이 매번 걸린다(정상인데) —
그리고 그 소음 뒤에서 진짜 버튼은 안 걸린다. **항상 같은 걸 잘못 짚는 검사기는
아무도 안 보는 검사기가 된다.**

## 못 잰 것 — 있는 그대로

`/map` 과 `/notes` 는 **이 컨테이너에서 렌더 자체가 안 된다.** Supabase 로 나가는
egress 가 막혀 있어 500 이 떨어지고, 그래서 fixed 요소가 0개로 잡혔다. 이건
"안전하다"가 아니라 "못 쟀다"다. 0개를 통과로 적지 않는다.

대신 소스 수준에서 확인한 것만 적는다. `/map` 의 하단 앵커 9곳과 상단 앵커 8곳은
**전부 같은 베이스를 거친다** — 하단은 `env(safe-area-inset-bottom)` 에서 출발하는
`--nz-map-bottom-lane`·`--nz-tabbar-offset`·`--nz-toast-bottom` 계열, 상단은 같은
방식의 상단 오프셋이다. 인셋이 붙으면 이 스택 전체가 **같은 값만큼 통째로**
올라간다. 게다가 standalone 은 세로를 110px 더 준다(734→844). 그래서 인셋 때문에
새로 생기는 겹침은 원리상 없다. 다만 이건 **논증이지 실측이 아니다** — 실기기나
egress 가 열린 환경에서 다시 재야 할 항목으로 남긴다.

## 결함 2 — 다크 모드에서 시스템 바 색이 안 따라왔다

`app/layout.tsx` 의 `viewport.themeColor` 가 `#f7f9fc` 한 값으로 박혀 있었다.
이 앱은 다크 모드를 손으로 켤 수 있고(`.dark` → `--bg: #0e1116`), 켜면 화면은
까만데 그 위 시스템 바만 밝은 회색으로 남았다. 탭 모드에서는 브라우저 UI 사이에
섞여 잘 안 보이지만, **standalone 에서는 그 띠가 곧 앱의 테두리라 바로 눈에 띈다.**

흔한 처방인 `themeColor: [{ media: "(prefers-color-scheme: dark)", ... }]` 는
**여기서 쓰면 더 나빠진다.** `ThemeProvider` 가 `enableSystem={false}` 라 이 앱의
테마는 OS 설정을 따라가지 않는다. OS 다크 + 앱 라이트(기본값이다)와 그 반대가
둘 다 정상 상태이고, 미디어쿼리는 그 두 경우에 **정확히 반대 색**을 칠한다.
그래서 새 컴포넌트 `app/components/ThemeColorMeta.tsx` 가 실제로 칠해진 `--bg` 를
읽어서 `<meta name="theme-color">` 에 넣는다. 색값을 이 파일에 복사하지 않은 건
globals.css 토큰이 바뀔 때 조용히 어긋나는 걸 저장소 다른 곳에서 이미 여러 번
봤기 때문이다(지도 레인 오프셋). 정하는 곳은 globals.css 한 군데, 여기서는 읽기만.
`--bg` 를 못 읽으면 아무것도 안 한다 — 빈 값을 써 넣으면 지금 맞는 색까지 잃는다.

### 이 결함을 고치다가 더 중요한 걸 하나 배웠다

첫 구현은 `useTheme()` 의 `resolvedTheme` 을 의존성으로 걸었다. **새로고침으로는
잘 됐다.** 라이트에서 `#f7f9fc`, 다크로 재접속하면 `#0e1116`. 코드 모양도 맞았다.
그런데 화면에서 토글을 누르는 **실제 경로**로 재 보니 이렇게 나왔다.

```
메뉴 열기 전: {"meta":"#f7f9fc","cls":"light"}
토글 후    : {"meta":"#f7f9fc","cls":"dark"}   ← 클래스는 바뀌었는데 색은 그대로
```

리액트는 자식 이펙트를 부모보다 먼저 돌린다. 이 컴포넌트는 `NextThemeProvider`
의 자식이라, 클래스를 붙이는 부모 이펙트보다 **먼저** 실행돼 아직 안 바뀐 색을
읽었다. 새로고침에서 통과한 건 next-themes 의 인라인 스크립트가 하이드레이션
전에 클래스를 이미 붙여 놓기 때문이다 — **그래서 새로고침 테스트로는 이 버그가
영원히 안 보인다.** 순서에 기대는 대신 색을 실제로 결정하는 것(`<html>` 의 class)을
`MutationObserver` 로 직접 본다. 고친 뒤 같은 경로로 다시 재서 양방향 확인했다.

```
메뉴 열기 전: {"meta":"#f7f9fc","cls":"light"}
토글 후    : {"meta":"#0e1116","cls":"dark"}
다시 라이트: {"meta":"#f7f9fc","cls":"light"}
```

**코드 모양이 맞아 보이고 새로고침으로 확인돼도, 실제 조작 경로로 재보기 전에는
됐다고 하지 않는다.**

## 문서와 코드가 갈라져 있던 곳

`docs/design-system.md:199` 는 `.safe-top` · `.safe-bottom` 을 안전영역 대응
클래스로 안내한다. 전수로 세어 보니 **이 두 클래스를 쓰는 화면은 한 곳도 없다.**
실제 대응은 전부 호출부가 `env(safe-area-inset-*)` 를 인라인으로 계산하는
방식이다(탭바 `max(6px, env(...))`, 지도 오버레이 `calc(env(...) + N)`, 로그인·가입
`max(20px, env(...top))`).

클래스를 지우지는 않았다. 대신 `globals.css` 의 선언 위에 **왜 안 쓰이는지와,
지금 얹어 쓰면 뭐가 깨지는지**를 적었다 — 이미 인라인으로 인셋을 더하고 있는
요소에 이 클래스를 또 걸면 홈 인디케이터에서 34px 이 두 번 붙어 빈 띠가 생긴다.
그리고 그건 **탭 모드에서는 인셋이 0이라 아무 일도 안 일어나고 조용히 지나간다.**
안내가 틀린 채로 남아 있으면 다음 사람이 그대로 밟는다.

## 재다가 스스로 밟은 함정 — 스테일 서버

토글 재측정이 갑자기 실패해서 회귀인 줄 알았다. 실제로는 `next start` 프로세스가
**빌드 이전 것이 그대로 살아 있었고**(`pkill` 이 exit 144 로 죽으면서 셸까지
같이 죽어 재기동이 안 됐다), 그 서버가 내려주는 HTML 이 새 빌드에 없는 청크
이름을 가리켜 JS 가 통째로 404 났다. 그때 프로브가 읽은 값은
`{"meta":"(없음)","cls":""}` — **결함처럼 읽히는 조용한 오독**이다. `curl` 은
200 을 돌려줬고 `tail` 로 자른 로그에는 콘솔 에러가 안 보였다.

`ps` 로 프로세스 시작 시각(00:32)이 빌드보다 이르다는 걸 보고 알았다.
**빌드했다는 것과 그 빌드를 보고 있다는 건 다른 말이다.** 재측정 전에는 서버가
언제 뜬 것인지 본다.
