# 소유자 보고 — 법정동코드(legal_regions) 3가지 문제

작성: 2026-07-27 · 대상: `public.legal_regions` 265행, `public.market_transactions` 656,272행

이 문서는 **결정을 요청하는 보고서**입니다. 여기 적힌 내용 중 제가 임의로 고친 것은 없습니다.
`legal_regions` 는 "어느 지역의 실거래를 받아올지" 를 정하는 표이고, 어느 코드가 정본인지는
사업 판단이라 소유자 결정 없이 건드리지 않았습니다. 또한 마이그레이션은 가산만 하는 규칙이라
행을 지우는 작업은 어느 경우에도 하지 않습니다.

실제로는 아래 1번, 즉 **라벨 오류**였습니다.

## 1. `lawd_cd 41430` 라벨 오류 — 시흥시가 아니라 의왕시입니다

`legal_regions` 에는 시흥시가 두 행 있습니다.

| lawd_cd | legal_regions 라벨 | 실제로 적재된 region_name | 행 수 |
|---|---|---|---|
| 41390 | 경기 시흥시 | 시흥시 | 8,764 |
| 41430 | 경기 시흥시 | **의왕시** | 3,198 |

국토교통부 법정동코드에서 41390 은 시흥시, **41430 은 의왕시**입니다. 그래서 41430 으로
API 를 부르면 의왕시 거래가 돌아오고, 적재된 3,198건은 `region_name` 에 "의왕시" 라고
**정확히** 들어와 있습니다.

### 그래서 지금 화면에 틀린 내용이 나가고 있지는 않습니다

세 가지를 확인했습니다.

1. **두 코드의 거래가 겹치지 않습니다.** 41390 과 41430 을 단지명·계약일·금액·면적·층으로
   교차 비교했더니 겹치는 행이 **0건**입니다. 같은 거래를 두 번 담은 게 아니라, 서로 다른
   두 도시의 거래가 각자 들어와 있습니다.
2. **화면은 `legal_regions` 를 보지 않습니다.** 실거래 지역 목록·지역 페이지·단지 페이지는
   모두 `market_transactions.region_name` 에서 나옵니다. 프로덕션에서 확인한 결과
   `/tx` 허브의 189개 지역 링크에 **시흥시와 의왕시가 각각 따로** 들어가 있고,
   `/tx/시흥시` 와 `/tx/의왕시` 둘 다 200 입니다.
3. **코드가 이미 이 중복을 우회하고 있습니다.** `lib/map/district-snapshot-store.ts` 의
   `resolveDistrictId` 는 (시도, 시군구) 가 유일하지 않다는 걸 알고 `lawd_cd` 오름차순 첫
   행을 고릅니다. 시흥시는 그래서 41390 — 맞는 쪽 — 이 뽑힙니다.

즉 지금은 **우연히** 안전합니다. 문제는 그 코드에 달린 주석이 41430 을 "법정동코드 재편으로
남은 옛 코드" 라고 설명한다는 점입니다. 그건 오진입니다. 41430 은 시흥시의 옛 코드가 아니고
의왕시의 현재 코드입니다. 이 주석을 근거로 나중에 누가 "옛 코드니까 정리하자" 며 41430 을
지우면, 의왕시 실거래 3,198건을 받아오는 경로가 사라집니다.

### 필요한 결정

41430 행의 라벨을 `경기 / 의왕시` 로 고칠까요? 그러면

- 시흥시는 41390 한 행만 남아 (시도, 시군구) 중복이 하나 사라집니다.
- 의왕시가 자기 이름의 행을 갖게 되어, 앞으로 지역 목록을 `legal_regions` 에서 만들 때
  의왕시가 빠지지 않습니다.
- 적재된 데이터는 손대지 않습니다 (이미 `region_name` 이 맞게 들어와 있음).
- 가산 규칙에 어긋나지 않습니다 — `update` 한 건이고 행을 지우지 않습니다.

제 판단으로는 고치는 쪽이 맞습니다. 다만 `legal_regions` 는 인제스트 대상을 정하는 표이니
"예" 라고 해 주시면 마이그레이션으로 반영하겠습니다.

## 2. 국토부가 응답하지 않는 코드 13개가 켜져 있습니다

`enabled = true` 인데 실거래가 **0건**이고, 앞으로도 0건일 코드들입니다.
국토부 실거래 API 는 구가 있는 시의 경우 **구 단위 코드로만** 응답하는데, 그 시의
**부모 코드**가 따로 등록돼 있습니다.

45111 은 1번과 달리 **진짜 옛 코드**입니다. 데이터가 0건이고 새 코드에 다 들어와 있습니다.

### 영향

화면에 틀린 내용이 나가지는 않습니다 (0건이면 그 코드로는 아무것도 안 그려짐). 대신
**인제스트가 매번 헛돕니다** — ETL 이 돌 때마다 이 13개 코드로 국토부를 호출하고 빈 응답을
받습니다. 지금 DB 가 Micro 급이라 인제스트 시간이 곧 조회 지연이 되는 상황이니, 줄일 수
있으면 줄이는 게 좋습니다.

### 필요한 결정

이 13행을 `enabled = false` 로 내릴까요? 행을 지우는 게 아니라 끄는 것이므로 되돌리기
쉽고, 가산 규칙에도 맞습니다. 45111 은 확실히 꺼도 되고, 부모 코드 12개는 혹시 국토부가
나중에 시 단위 응답을 시작할 여지를 남기고 싶다면 켜 두는 선택도 가능합니다.

## 3. 백필이 취소돼 비어 있는 지역 33개

`enabled = true` 인데 실거래가 0건이고, **코드는 맞는데 아직 안 받아온** 지역들입니다.
이전에 데이터 백필을 취소하셔서 그 범위가 비어 있습니다.

- **광주 5개 구 전부** — 동구·서구·남구·북구·광산구
- **인천 4개 구** — 중구·동구·서구·옹진군
- **세종시**
- **전남 22개 시군 전부** — 목포·여수·순천·나주·광양 + 담양·곡성·구례·고흥·보성·화순·장흥·강진·해남·영암·무안·함평·영광·장성·완도·진도·신안
- **경기 화성시**

화성시가 특히 눈에 띕니다 — 거래량이 많은 지역인데 0건입니다.

### 영향

이 지역들은 `/tx` 허브 189개 목록에 **안 나옵니다** (프로덕션에서 화성시·세종시·광주 북구·
인천 서구 모두 목록에 없음을 확인했습니다). 즉 "데이터가 틀린" 게 아니라 "그 지역이 아직
없는" 상태입니다. 사실 우선 원칙 관점에서는 지금 상태가 옳습니다 — 없는 걸 있는 척하지
않으니까요. 다만 광주·전남 전체와 화성시가 빠져 있으면 전국 서비스라고 말하기 어렵습니다.

### 필요한 결정

백필을 다시 돌릴까요? 돌린다면 두 가지를 함께 정해 주셔야 합니다.

1. **범위** — 33개 전부인지, 아니면 거래량이 큰 곳(화성시·광주 5구·세종·인천 4구)부터인지.
2. **시점** — 백필은 Micro 급 DB 에 부하를 줍니다. 지난번에 `market_transactions.raw` 통계
   수집이 8,600초를 태우면서 모든 조회가 밀린 일이 있었고(그건 마이그레이션으로 막았습니다),
   백필 자체의 쓰기 부하는 남아 있습니다. 트래픽이 적은 시간에 나눠 돌리는 쪽을 권합니다.

## 결정 및 처리 기록 (2026-07-27, 소유자 승인 후)

소유자가 1·2번을 승인해 아래와 같이 처리했습니다. **3번은 승인 대상이 아니었고,
백필은 여전히 돌리지 않았습니다.**

| # | 결정 | 처리 |
|---|---|---|
| 1 | 41430 라벨을 의왕시로 정정 | 마이그레이션 `20260727070541`(legal_regions) · `20260727070752`(districts) · `20260727071124`(좌표) |
| 2 | 응답 없는 13개 코드 끄기 | 마이그레이션 `20260727070541` + `lib/market/molit-transactions.ts` 의 `MOLIT_PARENT_ONLY_CODES` |
| 3 | 33개 지역 백필 | **하지 않음** — 소유자가 취소한 작업이고 승인받은 바 없습니다 |

### 1번을 고치다 발견한 것 — 좌표까지 함께 옮겨야 했습니다

41430 행은 원래 큐레이션 71행에 `scope='metro'` 로 들어 있었고 `lat/lng = 37.38 / 126.8029`
를 달고 있었습니다. 그 좌표는 **시흥시청 근처**입니다. 즉 이 행은 "시흥시를 잘못된 코드에
넣어 둔 것" 이었습니다. 이름만 의왕시로 바꾸면 지도에서 의왕시가 시흥시 자리에 찍히므로,
고치기 전보다 나빠집니다. 그래서

- 검증된 시흥시 좌표를 맞는 코드 **41390** 으로 옮기고 `scope` 도 `metro` 로 맞췄습니다.
- 의왕시 좌표는 **지어내지 않았습니다.** `complex_geocode` 에 실제 주소로 지오코딩된
  의왕시 단지 102곳이 있어 그 중심값 `37.3590 / 126.9741` 을 썼습니다. 같은 방식으로 계산한
  시흥시 327곳의 중심은 `37.3919 / 126.7831` 로, 위 큐레이션 좌표가 시흥시의 것이었다는
  교차 확인이 됩니다.

또한 `districts` 는 `legal_regions` 에서 시드된 표라 같은 오기가 복사돼 있었고, 그 결과
**의왕시는 `districts` 에 아예 없어서** 지도 스냅샷을 만들 수도 읽을 수도 없었습니다.
같이 고쳤습니다. 참조 행(`district_snapshots`·`ai_analysis_runs`)은 양쪽 다 0건이라
끊어진 참조는 없습니다.

### 2번에서 정정할 사실 — `enabled` 컬럼은 아무도 읽지 않습니다

`legal_regions.enabled` 를 `false` 로 바꾸면 수집이 줄 것으로 보고했지만, 실제로 확인해 보니
이 컬럼을 읽는 코드가 애플리케이션에도 DB 함수에도 **없습니다**. 수집 대상 목록은
`lib/national-data/region-codes.ts` 의 정적 표에서 나옵니다. 그래서 `enabled=false` 는
기록으로 남기되, 실제로 호출을 줄이는 변경은 `listMolitSigungu()` 에 제외 목록
`MOLIT_PARENT_ONLY_CODES` 를 둬서 했습니다 — 263개 → 251개.

빠지는 거래는 0건입니다. 12개 코드 각각의 적재량이 0건이고, 하위 구 코드가 정적 표에
전부 존재하며 거래를 다 갖고 있음을 확인했습니다(수원 22,866 / 용인 20,029 / 고양 18,115 /
청주 14,446 / 창원 14,320 / 천안 12,883 / 성남 12,691 / 안양 10,311 / 부천 10,246 /
전주 9,051 / 안산 6,837 / 포항 6,670). 45111(전주 완산구 옛 코드)은 정적 표에 애초에
없어서 `enabled` 만 껐습니다.

## 제가 하지 않은 것과 그 이유

- **행을 지우지 않았습니다.** `supabase/migrations/README.md` 규칙 1이 가산만 허용합니다.
  위 세 마이그레이션은 전부 `update` 이고 `delete` 는 한 건도 없습니다.
- **백필을 돌리지 않았습니다.** 지난번에 직접 취소하신 작업이고, 비용·부하가 따릅니다.
- **Supabase 컴퓨트를 올리지 않았습니다.** 결제가 걸린 일이라 소유자만 할 수 있습니다.
  (참고 사실: 측정된 `shared_buffers` 229 MB / `max_connections` 60 은 Micro 급이고,
  service_role 조회에 8초 statement timeout 이 실제로 걸립니다. 이 보고서의 몇몇 집계
  쿼리도 그 한도에 걸려 타임아웃 났습니다. 올릴지 말지는 사업 판단입니다.)
