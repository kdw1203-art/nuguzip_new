    | 분석 거부   | 요청 0건 · window.gtag 없음 |

    경우(StrictMode·재마운트) 1회차가 예약한 idle 을 cleanup 이 취소하고 2회차는
    `window.gtag` 가 이미 있어 통째로 빠져나가 **스크립트가 영영 안 실린다**.
    큐 생성과 스크립트 주입을 각자 멱등하게 분리해 해결.

    흐리지 않는다. 27(b)의 react `cache()` 와 겹쳐 두 겹으로 접힌다.
    **실패와 "기록 없음"은 캐시하지 않는다** — 값으로 돌려주면 unstable_cache 가
    한 시간 붙들어서, 크론이 첫 스냅샷을 쌓은 뒤에도 위젯이 최대 1시간 접힌 채로
    남는다. `lib/newui/digest.ts` 가 쓰는 수법대로 던진다(캐시에 남지 않고 다음
    요청이 재시도). 두 원인은 화면 결과가 같아도 로그에서 갈라 적는다
    (기록 없음 = warn · 조회 실패 = error). 안 그러면 "위젯이 안 보인다"를
    추적할 수 없다.

    저장소에는 디바운스가 180·200·250·280ms 로 흩어져 있었고, 값이 다른 이유는
    어디에도 없었다. 코드만 읽으면 "여섯 군데 다 디바운스 걸려 있음, 이상 없음"

    `scripts/measure-search-debounce.mjs` 로 속도 3종(120·220·380ms/자)을
    재현해 재 봤다. 여기서 함정 하나 — Playwright 의 `type()` 은 키 이벤트만
    쏘고 **조합 이벤트를 만들지 않는다.** 한글 글자를 넣어도 실제 한글 입력이
    아니다. 그래서 CDP `Input.imeSetComposition` 으로 2벌식 조합 상태를 그대로
    밀어 넣는 경로를 따로 만들었다(마지막 음절은 **일부러 안 닫는다** — 실제
    IME 가 그렇게 대기하기 때문).
    수정 전(4f2758c) 실측, /search 에 "래미안" 7키:
    | 간격 220ms | 1건 | 간격 380ms | **7건** — `["ㄹ","라","래","램","래미","래민","래미안"]` |
    380ms 는 낯선 단지명을 더듬어 칠 때의 흔한 속도다. 즉 통합검색(단지+매물+
    노트+뉴스 4종 조회)이 "ㄹ"로 한 번, "라"로 한 번… **여섯 번 헛돌았다.**
    아무도 "램"을 찾고 있지 않다.
    → 대기 규칙을 `lib/search/settle.ts` 한 곳으로 모으고(250ms · 조합 중
    500ms), 소비처 6곳을 전부 그 훅으로 바꿨다(HeaderSearch · search-client ·
    MapSearchBox · RegionPicker · ComplexPicker · NoteLocationSearch).
    검색어가 바뀌면 진행 중 요청은 abort 한다 — 늦게 온 옛 응답이 새 결과를
    덮으면 화면이 사용자가 치지 않은 말에 답하게 된다.
    **고르지 않은 해법을 적어 둔다:** "조합 중에는 아예 안 보낸다"가 제일
    간단해 보이지만 틀렸다. 한글 IME 는 마지막 음절 조합을 열어 둔 채 대기하므로
    사용자가 손을 떼도 `compositionend` 가 오지 않고, 그대로 막으면 **검색이
    영영 안 나간다.** 기능이 조용히 죽는 쪽이 요청이 좀 더 나가는 쪽보다 나쁘다.
    그래서 막지 않고 **더 기다린다**.
    수정 후 실측 — 한글 IME 경로: 입력창 3곳 × 속도 3종 **전부 1건**.
    비조합 입력(영문·숫자 상당)은 380ms/자에서 여전히 7건이다. 이걸 없애려면
    대기 시간을 380ms 위로 올려야 하는데 그러면 빠르게 치는 사람 전원이 매
    검색마다 그만큼 더 기다린다. **드문 느린 영문 입력을 위해 흔한 한글 입력을
    느리게 만들지 않기로 했고, 숨기지 않으려고 그 수치를 검사기가 매번 찍는다**

    - 스크립트가 읽는 `<html data-deploy-id>` / `data-csp-rev` 속성을
      app/layout.tsx 가 렌더한 적이 없음.
    즉 "탭 하나 = 시간당 1,200요청"은 **일어난 적 없는 일**이고, 주기를 30초로
    고친 것도 실행되지 않는 코드를 고친 것이다. 절약된 요청은 0건이다.
    구현 없이 약속만 있는 코드는 버그라는 원칙대로, 상수 두 개
    (`DEPLOY_SYNC_INLINE_SCRIPT`·`DEPLOY_RELOAD_PREFIX`)를 지우고 제거 근거를
    lib/security/deploy-sync.ts 에 기록했다. 같은 거짓 근거를 인용하던
    middleware.ts 주석 2곳도 함께 정정.
    살아 있는 stale 캐시 대응은 서버 단독으로 완결된다 — middleware 가
    CSP_REV_COOKIE 를 비교해 다를 때만 새로 심고 그 응답에 `Clear-Site-Data:
    "cache"` 를 싣는다. 공유 캐시로 나가는 문서는 `max-age=0` 이라 브라우저가
    재검증 없이 재사용하지 않으므로 비울 낡은 캐시 자체가 생기지 않는다.
    재도입한다면 (a) layout 에서 data-* 속성을 실제로 렌더하고 (b) 속성이 없을 때
    stale 로 판정하지 않도록 고친 뒤에 — 예전 스크립트는 속성이 없으면 stale 로
    봤으므로 그대로 배선했다면 전 방문자를 한 번씩 새로고침시켰다.

52. ✅ iOS "홈 화면에 추가" 안내 신설 — 화면을 실제로 넓히는 유일한 수단.
    소유자 제보(아이폰 사파리 스크린샷): "위 주소창·아래 도구막대가 화면을
    너무 많이 차지한다. 지울 수 있나?"
    사실 확인 — **웹 페이지가 사파리의 그 막대를 지우는 방법은 없다.**
    `apple-mobile-web-app-capable` 도, `minimal-ui`(iOS 8에서 폐기)도, 전체화면
    API 도 사파리 탭에서는 브라우저 UI 를 없애지 못한다. 실제로 사라지는 경로는
    **홈 화면에 추가**(manifest `display: standalone` 으로 실행) 하나뿐이고,
    390×844 기준 위아래 약 140px(≈16%)가 그대로 본문이 된다.
    문제는 그 경로가 **구현은 다 돼 있는데 아무도 안내하지 않았다**는 점이었다.
    manifest·apple-touch-icon·SwRegister 는 이미 있었고, 설치 배너
    (InstallPrompt)는 Chromium 의 `beforeinstallprompt` 에만 반응한다 —
    iOS 사파리는 그 이벤트를 구현하지 않으므로 아이폰에서는 **한 번도 뜬 적이
    없다**. 광고만 없고 기능이 없는 것과 반대로, 기능만 있고 안내가 없었다.
    조치: `app/components/IosInstallHint.tsx` 신설(안내 전용 — 공유 시트를
    코드로 열 방법이 없으므로 "설치" 버튼을 두지 않는다. 눌러도 아무 일 없는
    버튼은 없는 안내보다 나쁘다). 판정·공통 로직은
    `lib/client/pwa-install.ts` 로 뽑아 InstallPrompt 와 한 벌만 유지.
    노출 조건(넓게 띄우지 않기 위해 좁힌 것들):
    - iOS + Safari 인 경우만. iPadOS 13+ 는 UA 가 Macintosh 라 `maxTouchPoints`

    - **제외**: 카카오톡·네이버·인스타·라인 등 인앱 웹뷰(홈 화면 추가 메뉴가
      아예 없다), iOS 크롬·파폭·엣지(공유 시트 구성이 달라 안내가 틀린다).

    없는 페이지의 초록"을 거부해 정직하게 실패로 남긴 것이다. 기준선(내 변경을
    stash 한 상태)에서도 동일하게 실패한다 — 이번 변경과 무관하다.)
